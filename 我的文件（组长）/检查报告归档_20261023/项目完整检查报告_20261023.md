## 三、问题清单

### P1-1（真缺陷，建议 D1 前修）桥接层把 HR / RR 批次 / 信号质量全部丢掉，面板上的 HRV 口径与权威链不一致

**证据**

- `live_bridge.py:54` `FRAME_KEYS = ("theta","alpha","beta","delta","gamma","attention","meditation","rr_ms")`；
  `_clean()` 只按这个白名单输出（外加 gyro / ts / seq / source）。
- `source_serial()` 里 `on_rr()` 明明算了整批 `latest["rr_batch"]`，`on_eeg()` 也把它塞进了 frame ——
  **在 `_clean()` 这一步被过滤掉了**；`on_ext()` 写入的 `latest["hr"]` 更是从未进入过 frame。
- 前端 `js/app.js:386` `nextFrame()` 构造 `Frame` 时**不传 `heart`**；
  `js/engine.js:319` `this.rrBuf.push([frame.rr_ms, null, ts])`（+ `pushRR` 未被调用）—— 批次号写死 `null`。

**后果**

1. 一次 `onRR` 的 3 个连续间期，到浏览器只剩最后 1 个（丢 2/3）；
2. 引擎按 `batch=null` 做**跨回调差分**，量的定义已经不是 RMSSD 了。用合成 RR（800ms 基线 + 0.25Hz RSA + σ8 抖动）量化：

```
权威口径（批内 lag1 差分）  RMSSD = 24.14 ms
面板口径（跨帧末值差分）    RMSSD = 38.38 ms     偏差 +59.0%
```

RMSSD 系统性高估 → `z(RMSSD)` 偏高 → `Z_STRESS=-1.5` 更难越过 →
**面板上的 stress 会比 `serial_bridge` 上更难判出**；
3. 面板上根本看不到 `signal`（`app.js` 全文无 signal/质量字样）——D1 的 V3 信号档位判读只能回到 `serial_bridge` 侧做。

**这是本项目 v3.2 刚修过的同一个坑**（`serial_bridge.py:45–49` 有详细注释：只落盘 3 值里的最后 1 个 + 每个 RR 单独一个批次 → RMSSD 恒 nan）。Python 侧修了，前端与桥没同步。
`verify_parity` 抓不到：闸门 2 用的 `_diff_py.py` 帧序列只带单值 `rr_ms`、不带 `heart`，天然覆盖不到真机路径。

**修复（约 20 行，三处）**

```python
# live_bridge.py：白名单补三项 + _clean 透传
FRAME_KEYS = (... , "rr_ms", "rr_batch", "hr", "signal")
# on_eeg() 组装 frame 时补："hr": latest.get("hr")
```

```javascript
// app.js nextFrame()
rr_batch: Array.isArray(o.rr_batch) ? o.rr_batch : null, heart: o.hr ?? null
// 喂帧处：if (frame.rr_batch) frame.rr_batch.forEach(rr => eng.pushRR(rr, seq, ts))
```

```javascript
// engine.js _pushWindow()：支持 batch 入缓冲（与 Python _rmssd 的跨批 continue 语义对齐）
```

修完加一条 parity 断言：同一组「三值批次」帧，两侧 RMSSD 必须相同。

### P3-1 `serial_bridge --mock` 的断言偏弱，四相位里 stress 其实没判出来

mock 四相位为 focus / distracted / stress / relaxed，断言只要求「至少判出 2 个非 neutral」。实测两套快照都只输出：
`非 neutral 状态 ['distracted','focus','relaxed']` —— **stress 缺位**。

原因：mock 的 RR 用常量批 `(800+k%3*12, 808+…, 794+…)`，批内差分恒定 → RMSSD≈11.4 恒定 →
`z=(11.4-15)/5=-0.72`，够不到 `Z_STRESS=-1.5`。断言因此"绿了但没覆盖"。

**建议**：mock 的 RR 抖动按相位取值（stress 段 jitter 压到 3ms 以内），或断言改为「覆盖 ≥3 态且含 stress」。

### P3-2 `state_engine.py` 演示里 distracted 段全程显示"冷却中"，看起来像没有干预

`feedback_policy` 的冷却逻辑正确（60s 一次），但演示每 20 帧才打印一次，第一次 mild 提醒没被打出来，之后全落在冷却期。不影响判据，但**答辩现场讲解容易自相矛盾**（"这里应该提醒你回神"——屏幕上写着"冷却中"）。建议打印时机改成"状态变化时 + 每 20 帧"。

### P3-3（潜在）校准与运行的 RMSSD 口径不同源

- 浏览器校准 `engine.js:714` 用**帧级** `bs[i-1].rr_ms` vs `bs[i].rr_ms` 差分；
- Python 运行时 `state_engine._rmssd` 用**批内**差分。

当前纯 Python 解析器拿不到 RR，整条 HRV 链不可达，所以这条**现在是休眠的**。一旦切回官方 pyd（有 RR），会变成「校准基线偏高 → 运行时 z 偏低 → stress 偏敏感（假阳性）」。若要做，校准段也按三值批次喂。

> **后续状态（v3.4，2026-10-23）：已修复。** 校准改走 `RmssdWindow`，与运行时同源（同函数、同批内差分、同异位滤波、同 `RMSSD_MIN_PAIRS` 下限）；`verify_engine` E10 断言运行/校准 RMSSD 逐位相等（10.4658ms == 10.4658ms，差分对 38），旧实现此处恒为默认 15.0000ms（偏差 −89.2%）。`verify_rrpath` B 项同步校验双引擎同输入 RMSSD 一致。详见设计文档 §6.4②。

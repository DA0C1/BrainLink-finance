## 二、P0 — 影响方法学可信度（本轮已修）

### P0-1 校准失败被当成"已校准"，未校准横幅从此不再出现

**位置**：`js/app.js` `finishCalib()` / `isUncalibrated()`

**问题链**：
1. `finishCalib` 无论 `rep.ok` 真假都 `save('calibBase', …)`
2. `isUncalibrated()` 只判断 `calibBase` 是否存在
3. 于是**一次失败的校准**会让真机模式下"未校准"横幅永久消失，界面反而宣称已校准

**实测证据**（CDP 驱动，步长 5，快速协议）：

```
段样本 A/B/C = 3/8/8 帧 · ok = false
θ_ref = 55.0（来源 default）      ← 连 B 段参照都没取到
localStorage.calibBase 存在       ← 仍被保存
切到真机模式 → calibBanner.hidden = true   ← 横幅不出现
```

这正好是 P0-4（未校准横幅）想解决的问题，被自己的判据漏洞绕过去了 ——
**比"没有横幅"更糟：有横幅但永远不亮**。

**修法**（已实施）：
- `finishCalib`：`ok=false` 时**不落盘、不 `setBaseline`**，引擎回退原基线，报告照常显示告警
- `isUncalibrated()`：从"有没有存过 base"收紧为三条 —— 没存过 / `theta_ref_src === 'default'` / `meta.report.ok === false`

**验证**：
| 场景 | 修复前 | 修复后 |
|---|---|---|
| 失败校准 | 保存 + 横幅隐藏 | 不保存 + 横幅出现 |
| 成功校准（15/40/40 帧，ok=true，θ_ref=64.5 来源 B） | 保存 | 保存 + 横幅隐藏 |

## 三、P1 — 功能性缺陷（本轮已修）

### P1-1 校准时长跟着"演示步长"走

**位置**：`js/app.js` `calibCollect()`（原 `CAL.t += S.stepSec`）

**问题**：`S.stepSec` 是演示用的可调参数（1–5 s/帧，设置面板里暴露）。
校准按 `CAL.t >= targets[seg]` 切段，于是步长调到 5 时：

```
A 段目标 15s → 3 帧即结束（实测 framesToReachB = 3）
B 段 40s → 8 帧
C 段 40s → 8 帧
```

A 段只有 3 帧，δ 基线完全不可用；`ok` 判 False，再叠加 P0-1 就变成"失败被当成成功"。

**修法**：`CAL.t += 1`，校准固定按"1 帧 = 1 秒"计，与演示参数解耦（注释写明理由）。
真机 1.2–1.5s/帧时实际采集时长会略长于标称值，这对基线只有好处。

**验证**：步长 1 → A/B/C = 15/40/40（符合快速协议）；步长 5 → 同样是 15/40/40。

## 六、架构评估

### 6.1 合理的地方

1. **帧字段契约 + 双引擎对拍**是最有价值的架构决策。
   `live_bridge.py` 用 `FRAME_KEYS` 白名单出帧，`verify_frontend.py` 反向校验映射表不许多一个 key
   （typo 会静默失效），`verify_parity.py` 用 5 道闸门锁住 Python/JS 判据一致。
   本次复查中"engine.js 只加一个 `rrSeen` 标志"就能安全落地，靠的就是这套闸门。

2. **UI 不持有判据**。所有状态判定在 `state_engine.py` / `engine.js`，界面只读 `decision` / `feedback`。
   这轮 P0-1 的修法（改输出层、不动引擎）能成立，前提正是这条边界清晰。

3. **零前端依赖 + 便携 Python 运行时**，符合"组员解压双击即用、离线答辩"的真实约束。
   `runtime/` 96 MB 换来"不用装环境"，这个取舍是对的。

### 6.2 有风险的地方

1. **`app.js` 2348 行单文件 IIFE，7 项职责**（状态机 / 渲染 / 事件 / 校准 / 提醒 / 抽屉 / 导出）。
   零依赖约束下无法用 ES Module，但已到可维护性临界点：本轮 7 处修改全部落在这一个文件里，
   任何一处写错都会整页白屏（有兜底提示，但定位困难）。
   **建议**：按 `render.js` / `calib.js` / `remind.js` 拆成 3–4 个 IIFE 文件挂到同一命名空间，
   仍可无构建直接 `<script>` 引入，风险可控。

2. **全局可变状态 `S`** 无封装，任何函数都能直接改 `S.mode` / `S.phase` / `S.playing`。
   本轮就出现过"`__bs.S.mode='live'` 绕过 `setModeSeg`"的测试写法 —— 说明这个口子确实开着。
   **建议**：对这三个字段加 setter 校验（非法值直接抛错），其余字段维持现状。

3. **UI 层无单元测试**。判据侧有 verify_v26/28/29/30 四层，UI 侧只有 e2e 黑盒。
   `gradeLevel` / `noRRChannel` / `isUncalibrated` 这类纯函数完全可单测。
   **建议**：抽到 `js/logic.js` 并加 node 断言（本轮 P2-1 的 mild 重置问题，
   用 4 行断言就能覆盖，不必起浏览器）。

4. **`state_engine.py` 1655 行**承载解析/特征/判据/校准/日志五职责。
   但分区清晰、对拍要求单文件加载，**不建议拆**。

## 二、第二轮新发现（5 项，全部已修）

### P2-A 点模式按钮绕过了 `setModeSeg`，接触质量会串模式

`el.segMode` 的 click 处理器手写 `S.mode = b.dataset.mode` 与 active 切换，
没走 `setModeSeg()` —— 而"电极接触"格的状态文案正是在 `setModeSeg` 里刷新的。

**后果**：从真机切到「粘贴数据」后，指标格仍显示真机的 `signal` 读数（如"良好 30"），
而数据其实已换成模拟值。live 模式因为有逐帧 `updateSignal()` 掩盖了这个问题，
只有"切出真机"时才暴露。

**修法**：click 处理器改为调用 `setModeSeg(next)`，把 active/S.mode/接触质量三件事收敛到一个入口。

**实测**：切 live → `–/na`；切 paste → `模拟/na`（修复前恒为上一次的值）。

### P2-B 校准中途切数据源，基线会跨源拼接

`resetAll()` 重建引擎但不清 `CAL.buf`。切到真机后 `calibCollect` 继续往同一个 buffer 里
追加新数据源的帧，最终基线是「mock 的 A/B 段 + 真机的 C 段」。这比没有基线更危险 ——
报告会显示"校准完成"。

**修法**：`resetAll()` 开头检测 `CAL.active`，先 `cancelCalib()` 并提示
「数据源已切换，校准已取消（基线不跨数据源拼接）」。

### P2-C 文档里的桥端口写错（8765 vs 实际 8770）

`README.md` 与 `使用说明.md` 都写「校准抽屉填 `http://127.0.0.1:8765`」，
而 `live_bridge.py --port` 默认是 **8770**。照文档操作会连不上。

**修法**：两处改 8770。

### P2-D `live_bridge.py` 的示例参数用错

模块 docstring 第 3 条示例写 `--port COM5`，但 `--port` 是 **HTTP 端口**（`type=int`），
串口名要用 `--serial-port`。照抄会 `argparse` 直接报 `invalid int value`。

**修法**：改 `--serial-port COM5`，并在 `--port` 的 help 里点明两者易混。

### P2-E README 的真机步骤缺工作目录

1.1 节先让 `cd 任务一`，随后直接 `python live_bridge.py …` —— 而该脚本在 `项目文件/`。
按顺序执行会 `No such file`。

**修法**：改为推荐双击根目录的 `启动-实时面板.cmd`（已封装内置 Python 与正确参数），
手动方式注明"在 `项目文件/` 下执行"。

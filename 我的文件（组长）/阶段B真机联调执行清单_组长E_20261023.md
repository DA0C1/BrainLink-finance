### 1.2 找串口（这一步最容易白花一小时）

- Windows：设备管理器 →「端口（COM 和 LPT）」，记住 `COMx`
- macOS：`ls /dev/tty.usbserial-*`
- 波特率：**115200**（官方 sample 与说明书一致；注意这是蓝牙 SPP 链路速率，不是 TGAM 芯片的 UART 57600）

**BrainLink 配对后会生成两个虚拟 COM 口**（官方 FAQ 明确说明），必须选**「传出 / 输出」**那个：

- 选错的表现极具欺骗性：**端口能打开、不报错，但永远 read 不到一个字节**
- 分辨方法：蓝牙设置 →「更多蓝牙选项」→「COM 端口」，看哪个标着"传出"
- 配对时蓝牙列表里可能出现两个同名设备，**选名字前面带耳机图标的那个**

> **★ 实测更正：候选不止两个。** 本机 `list_ports` 枚举到 **COM1（主板自带通信端口）**。
> 也就是说列表里会有"传入 / 传出 / COM1"至少三项，**COM1 永远不要选**——它同样能打开、同样静默。

**现在有看门狗兜底了**（本次新增）：串口打开后 15s 内累计 0 字节会主动告警，
三种表现可直接判别：

| 你看到的输出 | 含义 | 处置 |
|---|---|---|
| `串口打开失败 ... FileNotFoundError` | COM 号不存在 / 未配对 | 回设备管理器确认编号 |
| `已打开` → 15s 后 `[警告] 已 15s 未收到任何字节` | **口选错了**，或头环没开会/被 App 占用 | 换另一个 COM；唤醒头环 |

### 1.4 signal 语义（★ 阻塞级修正，采集前必须知道）

`signal` 是 TGAM 的 **poorSignalLevel**，语义是 **0 = 信号最好，200 = 电极未接触皮肤，数值越大越差**。
（依据：NeuroSky《MindSet Communications Protocol》"The higher the number, the more noise is detected"；
ThinkGear Socket Protocol："0 indicating a good signal and 200 indicating an off-head state"。）

**本项目 v1.0 及以前的实现是反的**：`SIGNAL_GOOD = 200`、判 `signal >= 200` 为"良好"、
`--signal-min` 做下限过滤。后果是**真机上把好帧全丢、只放行"脱戴"帧**，而且离线合成数据
用 `signal=230`（已超 0–200 上限）恰好让这条错误判据永远通过 —— 测试自证，全绿却不是真的。

**已修（本次一并改完）**：

| 位置 | 改动 |
|---|---|
| `verify_hw.py` | 改为 `SIGNAL_OFFHEAD=200` / `SIGNAL_GOOD_MAX=100`；V3 判"已佩戴占比"，并加**反例·全程 signal=200 必须 FAIL** |
| `sdk_adapter.py` | `signal_min` → `signal_max`；`signal >= 200` 直接丢（硬门），超上限再丢 |
| `serial_bridge.py` / `live_bridge.py` | CLI `--signal-min` → **`--signal-max`**（旧参数会报未知参数，不会静默反向） |

**现场只需要记住**：`--signal-max 60` 意思是"signal 大于 60 就丢帧"，**数值越小门控越严**，
`0` = 不过滤。V3 跑完后按输出的 P90 定量取值。

校准报告三个数决定"能不能开跑"：

1. **`ok = true`**（伪迹率 <30%）—— 否则重戴，**不要带着坏基线开跑**
2. **`theta_ref_src = "B"`** —— 显示 `A-fallback` 或 `default` 都说明 B 段没采够，重采
3. **`c_anchor_z`** ≥ 门控值 → 放松态可判；否则该受试者的 relaxed 判据要标"降级"

导出的 `baseline.json` 一人一份，**不跨人复用**（θ、δ 的个体差异远大于组间差异）。

## 五、D4 录制 → 回放 → 调参（半天）

回放的意义是**离线调参不重采**：改判据后拿同一份数据重跑，看结论变没变。

```bash
cd 项目文件
# 录制（真机，带校准基线）
python serial_bridge.py --port COM3 --baud 115200 \
    --record data/rec_sub01.csv --baseline data/baseline_sub01.json

# 回放（加速，不等待）
python serial_bridge.py --replay data/rec_sub01.csv --speed 0 --baseline data/baseline_sub01.json

# 回放（实时，用于演示）
python serial_bridge.py --replay data/rec_sub01.csv --realtime
```

回放结尾会打印 `末态 / I_f / calmness / RR / RMSSD`。**必须检查 RMSSD 不是 nan**：

- `RMSSD=nan` + 提示"该 CSV 无 rr1–rr3 列" → 用的是 v3.1 以前的旧录制，属降级口径，重录可消除
- `RMSSD=nan` 且 CSV 有三列 → 说明 RR 每批只剩 1 个（引擎按批差分全断），查录制脚本

> **这是阶段 A 收尾时发现并修掉的真缺陷**：旧版录制只落盘 3 个间期里的最后 1 个，回放又用
> `onRR(rr,0,0)` 给每个 RR 单独一个批次号，导致 `_rmssd` 内相邻对全部跨批跳过、`diffs` 为空、
> **RMSSD 恒 nan**——而"RR 已入缓冲"这类弱断言照样通过。判据能跑、数据在，但压力特征静默失效。
> 所以回放一致性检查**必须看 RMSSD**，不能只看末态状态相同。

调参纪律（沿用任务认领清单）：**改引擎必跑三套回归**
（`verify_v26` / `verify_v28` / `verify_v29`）+ `verify_v30` + `verify_parity`；改前端引擎要额外跑 parity 的基线闸门。

## 六、D5 答辩（半天）

按 G3 大纲走：五段式 14 页 + 5 分钟演示脚本 + 故障预案。两个**必须主动交代**的点：

1. **优先级仲裁会压住"高分低优先"状态**（如高分 anxiety 遇边缘 stress 判 stress）——这是各状态评分量纲不同
   导致的刻意取舍，不是 bug。若被追问，说明"跨状态比 conf 等于比不同单位"
2. **真机样本量**：N=4–6 时 Wilcoxon 双侧最小 p 值为 0.125 / 0.0625 / 0.03125，即 **N≤5 无论效应多大都不可能
   p<0.05** → 本项目定位为**效应量报告**，不做显著性宣称

演示故障预案：真机连不上 → 立刻切 `live_bridge.py --source replay`（用已录数据循环），
话术是"现在切到回放模式展示同一份真机录制"，**不要说"刚才那是假的"**。

## 零、一句话结论

**EEG 主干可以直接自解析且已完成；心率/HRV 拿不到，代价是「8 态丢 1 态（stress）」。**

不是"可行/不可行"的二选一，而是按数据通道分裂：TGAM 标准帧（公开规范）全部拿到了，
BrainLink 私有扩展包（无任何公开规范）全部拿不到。所以真正要决策的只有一件事——
**你愿不愿意用 stress 这一态，去换"不依赖一个 3.11 的闭源二进制"**。

## 一、先看现实：官方 pyd 的可获得性

| 事实 | 来源 | 判定 |
|---|---|---|
| 仓库只有 `BrainLinkParser.pyd` + `.so`，**无任何 Python 源码** | GitHub 仓库文件列表（本地搜索缓存 + 镜像站一致） | 闭源二进制 |
| README 明确写 **"Python Version Python 3.11"** | 官方 README | 与目标解释器绑定 |
| 本机只有 **Python 3.13.14**（实测 `py --list` / `sys.version`） | 本机执行 | 版本不匹配 |
| GitHub raw / 仓库主页在本机**超时不可达** | 本机 `urllib` 实测 | 拿不到 zip 核对 .pyd 文件名 |
| PyPI 可达，但 pip 默认源（清华镜像）**不可达** | 本机实测 | 见 §6 的坑 |

结论：**3.13 下 import 成功的概率很低**，且没有源码可改。这不是"再试一次"能解决的问题。

> 附带发现（与本评估无关但阻塞 D0）：`pip install pyserial` 在本机会报
> `Could not find a version that satisfies the requirement pyserial (from versions: none)`——
> 看起来像"包名写错/包不存在"，**实际是镜像源不可达**。用官方源即可安装成功（已实测）。

## 二、可行性分级（按数据通道，这是本评估的核心）

| 通道 | 协议归属 | 可行性 | 依据 |
|---|---|---|---|
| signal / attention / meditation | TGAM 标准段 `0x02/0x04/0x05` | ✅ **已实现** | 协议公开 |
| δ θ lowα highα lowβ highβ lowγ midγ | TGAM 标准段 `0x83`（8×24bit 大端） | ✅ **已实现** | 三方来源一致 |
| raw 原始波 | TGAM 标准段 `0x80`（有符号 int16） | ✅ **已实现** | 协议公开 |
| **heart（bpm）/ ap / battery / gnaw / temperature** | **BrainLink 私有扩展包** | ❌ **不可行** | 无公开规范 |
| **RR 间期（rr1–rr3）/ 血氧** | **BrainLink 私有** | ❌ **不可行** | 见下方三点 |
| gyro（x,y,z） | BrainLink 私有 | ❌ **不可行** | 无公开规范 |

RR 为什么比 EEG 更没戏，有三条独立证据：

1. **TGAM 规范里没有 RR**。TGAM 只输出 eSense + 8 段功率 + raw，PPG/心率是 BrainLink
   自己加的传感器，数据走私有包。
2. **Android SDK 的接口形态就说明了它不是标准段**：
   `onRR(String mac, ArrayList rr, int oxygen)` —— RR 是**变长列表**还带**血氧**，
   与 TGAM 的定长段机制完全不同。
3. **Python SDK 根本没有下发指令的能力**。Android 侧靠
   `setDataType(mac, DATATYPE_...)` 主动开启各类数据输出；而 Python SDK 的
   `BrainLinkParser` **只有 `parse()` 一个方法**，无法下发任何命令。
   → 即使上了官方 pyd，**设备默认是否推送 RR 也无法从 Python 侧控制**，需现场实测确认。

> 第 3 点是个被忽略的风险：它意味着"装了官方 pyd 就一定有 RR"是不成立的假设。
> D1 首次联通时必须实测 RR 是否真的到达，不能等 V1 才发现。

## 四、降级影响量化（对照实验，不是推断）

用同一份合成形态，**只切换"灌不灌 RR"**，看引擎判什么：

| 输入形态 | 无 RR（纯 Python 路线） | 有 RR（官方路线） | 判据依据 |
|---|---|---|---|
| focus | focus 0.95 | focus 0.95 | R_tb，与 RR 无关 |
| **stress** | **neutral 0.60（判不出）** | **stress 0.95**（RMSSD 3.2ms） | `z(RMSSD_60) < -1.5` 是硬条件 |
| anxiety | anxiety 0.95 | anxiety 0.95 | eSense 双低常模，不依赖 RR |
| distracted / relaxed | 均正常判出 | 均正常判出 | R_tb / A_rel |

再补一条静态证据（不依赖实验）：`state_engine.py` 里 stress 的判据是

```python
"stress": z.get("RMSSD_60", 0) < Z_STRESS and (...)   # Z_STRESS = -1.5
```

RMSSD 缺失时 `z` 里没有该键 → 取默认 `0` → `0 < -1.5` 恒为假 → **stress 不可能被判**。
这与上面的实测完全一致。

### 结论：8 态里丢 1 态

- 丢失：**stress**（HRV 主判据失效）
- 保留：focus / distracted / relaxed / anxiety / fatigue / drowsy / flow（均不依赖 RR）
- 缺失 gyro 的连带影响：`still` 特征恒为 0（`still=0.0`，实测），体动平静门控**形同虚设**。
  方向偏"松"（更容易判 focus/stress），不会误拒；但说话/动作伪迹只能靠 EEG 伪迹门拦，
  **不能靠 gyro 辅助** → 这正是 V4 肌电专用门在纯 Python 路线下**价值更高**的原因。

> 未复现项（如实记录）：`flow` 在合成数据上判成了 focus，但**有 RR 时同样判 focus**，
> 所以与解析器无关，是我的合成分量不满足 `flow_hold`/`sync` 条件。不据此下任何结论。

## 五、工作量：实测值

| 项 | 实测 |
|---|---|
| `tgam_parser.py` | **339 行**（含协议注释、诊断计数、自检） |
| `verify_tgam.py` | **102 行** |
| 核心解析逻辑 | ~120 行（帧同步 + 校验 + 5 类段） |
| 自检用例 | 13 项（含 5 条反例） |
| 接入改动 | 每个 bridge 约 8 行（try/except + 打印来源） |
| **现场若从零自己写** | 半天到一天（含调试校验和/半包/重同步） |

**注意这活儿真正的成本不在写代码，在"知道该按什么写"**：帧格式必须三方交叉验证
（NeuroSky 协议文档 + TGAM datasheet + 实测抓包），凭记忆写会写出"看着能跑但字节错位"的解析器。
本机已完成并固化，现场直接用即可。

已内置的现场诊断（这一项在真机排障里价值最高）：

```python
parser.health()
# → 帧 1520｜EEG 回调 1500｜校验错 3｜长度错 0｜重同步丢弃 41 字节｜未知段 0x5A×12｜raw 0
```

"没数据"时靠它能立刻分清是**没收到字节**、**校验全错（波特率/线路）**、还是**段不认识（协议变体）**，
不用瞎猜。

## 六、三条路线对比与推荐

| 路线 | 成本 | 拿到 RR/心率 | 主要风险 | 适用 |
|---|---|---|---|---|
| **A. 纯 Python 自解析**（已就绪） | 0（已完成） | ❌ | 真机帧格式若有变体，需现场用 `health()` 定位 | **首选**：先跑起来，6 态 + anxiety 可用 |
| B. Python 3.11 便携版 + 官方 pyd | 装 3.11 + 重装 pyserial，约 1–2 小时 | 需实测确认（见 §2 第 3 点） | 两套解释器并行，命令易混；pyd 仍需 cp311 | 只有"必须拿 HRV"时才值得 |
| C. 抓包逆向私有包 | 数天，且无规范保证 | ✅（理论上） | 不确定性极高，可能白做 | 不建议，除非有明确研究需求 |

### 推荐：**A 打底，B 作可选增强**

1. 阶段 B 直接用 A 跑通 D1–D4。**stress 判据标注为"降级为不可用"**，README 与答辩同步说明。
2. 如果后续确实需要 HRV（例如 V1 必须给出 RMSSD 结论）：
   - 先装 3.11 便携版跑 B，**用 `parser.health()` 之外的手段确认 RR 真的到达**（打日志看 `on_rr` 是否被调用）
   - 能到 → 用 B 重采 V1 数据；到不了 → 说明设备/Python SDK 不下发开启命令，B 也白搭，直接放弃 HRV
3. C 不进计划。

**关键判断**：A 和 B 不是等价选项。A 是"确定拿到 6 态 + anxiety，明确丢 stress"；
B 是"可能全拿，也可能连 import 都失败、或 import 成功但 RR 不来"。**先做确定的那个。**

## 七、剩余风险（必须在 D1 现场验证）

| # | 风险 | 怎么验 | 不成立时怎么办 |
|---|---|---|---|
| 1 | 设备实际不出 `0x83` 大包（只发 raw） | 看 `health()` 的"EEG 回调"计数是否为 0 | 加 raw→频段自算（成本高，属新功能，需单独立项） |
| 2 | 校验和变体（部分固件不校验/异或校验） | `health()` 里"校验错 ≈ 帧数" | 加 `--no-checksum` 开关，但会失去坏包防护 |
| 3 | 0x83 段长度 >24 的变体 | `health()` 里 `0x83/bad_len` 计数 | 已按声明长度前进，兼容；若报 bad_len 需抓包看实际结构 |
| 4 | 出现大量未知段（私有包） | `unknown_seg` 明细 | 属预期（心率/RR 就在里面），不影响 EEG |
| 5 | 波特率不是 115200 | 全是重同步丢弃、帧数 0 | 试 57600（TGAM 模块 UART 原生速率） |

## 2. P0：必须先修的两处静默失效

### P0-1 `ts=0` 被当成"没有时间戳"，窗口从此不再滑动

**位置**
- `项目文件/state_engine.py:1138`：`ts = frame.ts if ... and frame.ts > 0 else self._clock()`
- `项目文件/state_engine.py:733`：`ts - (self.eeg_buf[0].ts or ts) > WINDOW_EEG_S`
- `组员文件/任务一/js/engine.js:869` / `:527` 同一写法（JS 默认时钟从 1 开始，暂时没触发）

**实测**

```
首帧 ts=0.0  → 100 帧后 eeg_buf=100（应为 9），gyro_buf=100（应为 26）
首帧 ts=0.1  → eeg_buf=9，gyro_buf=26
```

原因：首帧 ts=0 被判为缺值 → 回退 `time.time()`（1.79e9）；后续帧 ts=1.2/2.4 相对它
是"几十年前"，`ts - buf[0].ts` 恒为负 → 永不裁剪。更隐蔽的是第二处：
`self.eeg_buf[0].ts or ts` 里 0 是假值，即使首帧 ts 保留 0，比较也会退化成 `ts - ts = 0`。

**影响**
- 任何首帧 `ts=0` 的 CSV 回放（`serial_bridge --replay`）整段退化为"全程累计平均"：
  状态切换被抹平，I_f / 确认窗口 / 冷却全部失真，且**不报错**。
- 缓冲线性增长 → 每帧 `_extract` 遍历全历史，O(n²)。实测 5,000 帧时 0.558 ms/帧
  （正常 0.068 ms），50,000 帧超过 120 秒仍未跑完。
- 现有 `verify_engine.feed(ts0=0.0)` 正好落在这个分支，所以窗口裁剪**从未被真正测到**（见 P1-3）。

**建议**
```python
# process_frame
ts = (frame.ts if frame.ts is not None and math.isfinite(frame.ts) and frame.ts >= 0
      else self._clock())
if frame.ts is None or frame.ts < 0:
    frame.ts = ts

# _push_window
first = self.eeg_buf[0].ts
while self.eeg_buf and ts - (first if first is not None else ts) > WINDOW_EEG_S:
    self.eeg_buf.pop(0)
    first = self.eeg_buf[0].ts if self.eeg_buf else None
```
JS 同步改 `frame.ts != null && frame.ts >= 0` 与 `eegBuf[0].ts != null ? ... : ts`。
补一条边界用例：ts=0,1,…,11 后断言 `len(eeg_buf)==10`（ts=0 那帧在 11s 时刚出窗）。

> 当前交付的真机 dump 首帧 t=3,447 ms，所以已验收结论不受影响；这是一颗"换一份
> 从 0 开始的录制就会踩"的雷。

### P0-2 数据源线程死了，HTTP 仍宣称 `ok:true`

**位置**：`项目文件/live_bridge.py:596`（裸线程启动）、`:442`（`/health` 硬编码 `ok: True`）

**实测**
```bash
python live_bridge.py --source serial --serial-port COM_DOES_NOT_EXIST --port 8798
# 2 秒后：
curl /health → {"ok": true, "source": "serial:COM_DOES_NOT_EXIST", "frames": 0, ...}
# 日志为空（stdout 重定向时被缓冲）
```
`source_serial` 打不开串口时 `raise SystemExit(...)`；`threading` 会**静默吞掉**线程里的
`SystemExit`，HTTP 服务继续跑。UI 的 SSE 连接是 open，于是显示"已连接"，但永远没有帧；
6 秒后链路提示条还会说"蓝牙卡顿/设备休眠"，把"COM 选错"误诊成"设备掉线"。

**影响**：现场最高频的失败（选错 COM / 没有 pyserial）变成"看起来正常"。这比崩溃更贵。

**建议**
```python
def _run_source(fn, broker):
    try:
        fn()
    except BaseException as exc:          # 含 SystemExit
        broker.error = f"{type(exc).__name__}: {exc}"
        print(f"[bridge] [致命] 帧源已停止：{broker.error}", file=sys.stderr, flush=True)
    finally:
        broker.alive = False

broker.alive = True
threading.Thread(target=_run_source, args=(target, broker), daemon=True).start()
```
- `/health` 返回 `{"ok": alive and not error, "alive": ..., "error": ..., "last_frame_age": ...}`
- 前端 `refreshDiag()` 读 `alive/error`，红条显示"帧源已停止：…"，而不是继续显示"连接中"
- 启动前预检：serial 源先 `import serial` 并试开串口，失败直接 `exit 2`；replay 源已校验文件
- 端口占用 `OSError` 也给可执行提示（"8770 已被占用，先关掉旧实例"）

## 3. P1：显著影响可用性与可信度

### P1-1 新连接先回填 600 帧（约 10 分钟）旧数据

**位置**：`live_bridge.py:481`（`seq = 0`）+ `Broker(keep=600)`

**实测**：桥跑了 8,958 秒后，新开一条 SSE：
```
2 秒内收到 603 个 data 帧（600 回填 + 3 实时）
```
浏览器队列上限 300，于是丢掉最早 300 帧、保留最近 300 帧——**仍然是 5 分钟前的数据**。
`lastGap` 按这些帧的历史 ts 计算（约 1s），界面会用约 37 秒"补课"，期间曲线、状态、
提醒全部是旧的。

**建议**：新连接从 `broker.latest_seq` 开始（只推实时）；需要补历史时显式
`/stream?backfill=60`，并限制在 60 帧/60 秒内。UI 不需要改。

### P1-2 校准 σ 与运行时特征不是同一个估计量（上一轮已提，仍未决）

校准用逐帧特征估 μ/σ，运行时用 10 秒窗均值再算 z。同一 D2_B 段：

```
R_tb  逐帧σ=2.058  10s窗σ=0.684  3.01×
R_ba  逐帧σ=0.354  10s窗σ=0.105  3.38×
alpha 逐帧σ=14576  窗σ=4760      3.06×
```

运行时 |z| 被压缩约 3 倍；`Z_CONC=-1.0` 在逐帧空间是 16% 分位，窗口空间只剩 0.13%。
实测 D2_B 122 帧里 **focus 判 0 帧**。这不是阈值问题，是两把尺子。
**建议**：校准侧也按 10s 滑窗生成特征；Python/JS 同改，重跑 8 段主判率与对拍。
需要先出一份"改前/改后"对照，确认灵敏度提升没有换来不可接受的误报。

### P1-3 测试的时间基准是错的，窗口行为实际未被覆盖

**位置**：`verify_engine.py:41`（`feed(..., ts0=0.0)`），以及多处 `ts=float(i)` 从 0 开始。

因为 P0-1，这些 fixture 的第一帧跳到墙钟，后续帧全部"在过去"，10s 窗退化为累计窗。
E3 声称验证"δ 走 10s 窗均值"，但在累计窗下同样通过——**断言是真的，被测行为是假的**。
13 个脚本里没有一处断言 `len(eeg_buf)` 在稳定后应为 9。

**建议**
1. 先修 P0-1；
2. `feed` 默认 `ts0=1.0`（或修好后保留 0，但显式声明）；
3. 新增 `e_window_boundary`：ts=0..11 后断言缓冲 10 帧、`f.delta` 等于 10 帧均值；
4. 新增 `e_window_bug_regression`：首帧 ts=0 时缓冲仍必须收敛到 9。

### P1-4 两套 CSV 回放实现已经漂移

**位置**：`serial_bridge.run_replay`（Python 引擎）与 `live_bridge._row_to_frame`（浏览器引擎）。

同一行 CSV 的默认值不同：

| 字段 | `run_replay` | `_row_to_frame` |
|---|---|---|
| `signal` 缺列 | `0`（当作完美接触） | `None`（当作未知） |
| `rr_ms` 有 `rr1–3` | 取批首 | 取批尾 |
| `gyro` 缺列 | 不调用 `onGyro`，沿用初值 | 恒写 `[0,0,0]` |
| 低/高α 合并 | 手写 | 另一段手写 |

两处都"看起来对"，但修接触帧、修 RR 批次时只改了一边（本轮的接触帧只加在 `live_bridge`）。
**建议**：抽 `frameio.py`，`csv_row_to_frame(row) -> dict` 为唯一转换；`run_replay` 用它构造
`Frame`，`_row_to_frame` 直接返回它。再加一条"同一 CSV 两侧产出字段逐项相等"的测试。

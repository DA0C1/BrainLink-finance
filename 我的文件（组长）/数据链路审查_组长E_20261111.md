# 数据链路审查（组长 E · v3.15 · 2026-11-11）

审查对象不是"判据选得对不对"（那是《状态引擎设计评估》），而是**每一个输入字段从字节到结论
被怎么对待**：单位、缺值表示、范围校验、时间基准、以及在两套引擎/三个入口（串口、回放、
粘贴）之间是否一致。

方法：逐字段读代码 + 用 5 份真机 dump（1876 帧）做分布统计 + 构造异常帧实测行为。
新增 `verify_data.py` 把 7 组检查固化下来（27 项，全部通过）。

## 二、P1（会影响结论，已修 2 项 / 未修 1 项）

### P1-1 校准 σ 与运行时特征不是同一个估计量（**未修，需决策**）

- 校准：`calibrate_from_frames` 用**逐帧**特征估 μ/σ（B 段 122 帧）。
- 运行时：`_extract` 用**10 秒窗均值**再算比值，然后拿校准 σ 做 z。

同一段 D2_B 上实测：

| 特征 | 逐帧 σ | 10s 窗 σ | 比值 |
|---|---|---|---|
| R_tb | 2.058 | 0.684 | **3.01×** |
| TAR | 2.072 | 0.836 | 2.48× |
| R_ba | 0.354 | 0.105 | **3.38×** |
| alpha | 14576 | 4760 | 3.06× |
| delta | 167192 | 70692 | 2.37× |

中位 **3.01×**。含义：运行时 z 被同比例压缩。`Z_CONC = -1.0` 在逐帧空间是 16% 分位，
在窗口空间只剩 **0.13%**（Φ(−3)）。这与实测吻合：**D2_B（睁眼任务段）122 帧里
focus 判定 0 帧**（neutral 104 / distracted 12 / drowsy 5）。

这不是"判据太严"，而是**基线的尺子和运行时的尺子不是同一把**。同样的失效模式此前
在 RMSSD 上修过一次（校准帧→帧差分 vs 运行时批内差分），这是它在其它特征上的残留。

**建议改法**（会动到全部基线，所以没有擅自改）：`calibrate_from_frames` 内部先按
10s 滑窗生成特征序列，再估 μ/σ；Python/JS 两侧同改，重跑 8 段主判率与
`verify_parity`。预计效果是阈值恢复设计灵敏度（focus/distracted 从"几乎不可达"回到
各约 16% 的分位），但也会抬高误报，需要重新验收。

### P1-2 eSense=0 被当成"极度焦虑"（已修）

实测（20 帧，正常频段，仅 att=med=0）：

```
修前：anxiety  conf 0.95   （anxiety 优先级仅次于 stress）
修后：neutral  conf 0.60
```

TGAM 在信号差或指数尚未算出时会同时给 0/0。这不是"双低"，是"没有指数"。
真机数据里也有 `signal=26` 的帧（att=8/med=43），说明指数会随接触质量波动。

修法（两引擎同步）：
- 焦虑门控（含绝对常模与 z 两个分支）要求 `attention > 0 且 meditation > 0`；
- 同步率窗口跳过 eSense 无效帧（否则 60→0 的伪跃变会被算成一次"同向下降"）；
- 校准 B 段的 att/med 统计剔除 ≤0 的值（否则几帧缺失会把基线下拉）。

### P1-3 接触帧被丢在服务端 → 界面"未接触"永不出现（已修）

`source_serial` 原实现 `if signal >= 200: return`，帧根本没进 SSE。后果有三：

1. 界面只有"蓝牙卡顿/设备休眠"这一种解释，分不清"贴片掉了"和"链路断了"；
2. 校准报告里的「接触无效占比」恒为 0 —— 统计对象被上游丢了，**这个 0 是假的**；
3. 事后回看，接触不良的时段在数据里只剩"时间缺口"，没有原因。

修法：接触帧照常下发（`source=serial:contact`，`signal=200`），前端 `contactBad()`
在入窗之前拦掉，不污染判别；校准器会把它计入 `contact_hits`。

## 三、P2（已修 4 项 / 未修 3 项）

### 已修

| 问题 | 证据 | 修法 |
|---|---|---|
| **JS 把 null 读成 0** | `Number(null) === 0`，`num(null, 50)` 返回 0 而不是 50；服务端 `_clean()` 正是用 `null` 表示缺值 | `num()` / `pick()` 对 `null`/`""` 走默认值 |
| **SSE 队列跨模式积压** | 停在「自动轮播」时桥仍在收帧，队列上限 300（约 5 分钟）；切回真机先判几百帧过期数据 | `LiveBridge.flush()`；连接/断开/进入真机时清空 |
| **回放 CSV 未排序** | 乱序 ts 会让 `ts - buf[0].ts` 变负 → 窗口不裁剪、确认权重为负 | `run_replay` / `source_replay` 先按 ts 稳定排序（实测末帧 ts=3.0 正确） |
| **`Frame(gyro=None)` 崩溃** | `_extract` 里 `g[0]` 抛 TypeError；而"没有陀螺仪"最自然的写法就是 None | `Frame.__post_init__` 归一化为三元组 |

### 未修（记录 + 理由）

**P2-3 长断流后单帧即可通过时间确认。** 直接实测：

```
t=1.2 focus → focus
t=2.4 focus → focus
t=32.4 relaxed → relaxed   ← 中间断 30s，仅 1 帧
_hit_buf: [('relaxed', 32.4, 2.4)]   ← 30s 被算成了 relaxed 的持续时间
```

`_confirm` 把 `[prev_ts, ts]` 整段归给当前状态，且窗口内只剩 1 条时直接返回状态。
结果：断流越久，恢复后第一帧越容易"秒确认"。属判据逻辑（改动会影响
`verify_engine` 的确认用例），没有在本轮动。建议：把单条权重上限压到 2–3s，
或当 `total == 0` 时返回 neutral。

**P2-6 RR 三元组每行重复。** 模拟"EEG 1.2s/帧、RR 每 3 帧一次"录制 90 行：
**67% 的行与前一行 RR 完全相同**。实测回放 RMSSD 不变（5.98 vs 5.98），因为重复批内
差分相同；但差分对数从 90 变 270，60s 窗"更早填满"、`len(rr_buf)` 虚高。
建议录制时只在**新批次到达**的那一行写 rr1–rr3（空表示沿用），或加 `rr_seq` 列。
本机无 RR 通道，这条目前不影响真机结论。

**P2-7 HR 基线口径不一致。** 校准用 `60000/fr.rr_ms`（逐拍瞬时），运行时用 60s 均值
RR 或 heart EWMA。前者 σ 大、后者平滑，z(HR) 会系统性偏小。本机没有 RR/PPG，
`HR` 恒 nan 不参与，属"换设备才会暴露"的问题。

## 四、P3（记录，不改）

1. **parser 遇未知段直接 `break`**：TGAM 私有段长度未知，无法安全跳过；若它出现在
   0x83 之前，本帧的频段会丢。真机 1876 帧未出现（频段齐全），`stats["unknown_seg"]`
   已在诊断里留痕。要彻底解决需逆向私有段长度，不建议。
2. **缺陀螺仪 = 完全静止**：`still=0`，默认基线下 z(still)=−2.5，给 relaxed 分数
   +1.25、distracted −1.25。只影响界面显示的 8 态分数，不影响仲裁与 conf（两者都不读
   `still` 的分数项）；校准后 `still` 的 σ→sigma_min，z=0，偏差消失。
3. **伪迹参照前 5 帧无法判定**：`ARTIFACT_REF_MIN` 未满时 `ref()` 回退 smooth，首段
   5 帧不会被判伪迹。校准伪迹率因此略偏低（32 帧的 A 段约 16% 未判）。
4. **`_row_from` 的 `frame.ts or time.time()`**：ts=0 被当缺值；回放首帧会拿到墙钟，
   导致第二帧 `lastGap` 为负、退回 stepSec。只影响首两帧。
5. **`export_csv.to_row` 直接下标取键**：缺列的 eeg 行会 KeyError 中断整段导出
   （`_fnum` 只保护了回放侧）。

## 七、结论与建议顺序

数据入口的**强制校验**做得扎实：校验和、长度上限、重同步、接触硬门、伪迹双向门、
生理范围过滤、时间窗裁剪，每一层都能指出对应的实测事故。真正的问题集中在
**"缺值用什么表示"**和**"校准与运行时是否同一把尺子"**：

1. ~~eSense=0 / 接触帧 / null→0~~（已修，风险最低、收益最直接）
2. **P1-1 估计量统一**（收益最大，但会改全部基线；建议单独一轮，先出对照报告再合并）
3. P2-3 确认窗口的断流归属（改判据逻辑，需补用例）
4. P2-6 RR 录制去重（本机无 RR，优先级最低）

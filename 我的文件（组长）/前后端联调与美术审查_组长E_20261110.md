## 一、前后端运行检查（实测）

### 1.1 服务端接口面

| 路径 | 方法 | 用途 | 消费方 |
|---|---|---|---|
| `/stream` | GET | SSE 帧推送（`FRAME_KEYS` 14 字段 + seq/ts/source） | `js/bridge.js:46` |
| `/stream` | HEAD | 只回头部（v3.8 修复：原来会进无限循环） | 探测脚本 |
| `/health` | GET | `ok/source/frames/clients/uptime` | **无前端消费**（见 P1-3） |
| 其余 | GET | 静态文件（`js/` `css/` `index.html`），带路径穿越防护 | 浏览器 |

**没有 POST 接口** —— 校准、基线、设置全部在浏览器端完成，服务端只负责"把帧推过去"。
这是刻意的：演示现场不需要后端状态，断电重启即恢复。

### 1.2 数据流（三源合一）

```
mock 源 ─┐
serial 源 ├─► Broker（环形缓冲 + 每客户端游标）─► SSE ─► LiveBridge ─► nextFrame() ─► Frame ─► 引擎 ─► 渲染
replay 源 ┘
```

逐段验证结果：

| 环节 | 断言 | 结果 |
|---|---|---|
| Broker 发布 | 6 帧内 `seq` 单调不重复 | ✓ `[1,2,3,4,5,6]` |
| SSE 首帧时延 | 10s 内至少 3 帧 | ✓ 6 帧 |
| 字段完整性 | `FRAME_KEYS ∪ {gyro,seq,ts,source}` 全在 | ✓ 14 字段齐 |
| 前端接帧 | 帧数递增、仿真时钟推进 | ✓ 69→89 帧、89s→101s |
| 引擎判定 | 状态/置信度随数据变化 | ✓ 专注→心流→放松 |
| 接触质量 | 真机模式显示 `良好 30` | ✓（修 P0-1 后） |

## 七、复跑方法

```bash
cd 项目文件

# 接口联调（自起服务、自断言、自清理）

# 前后端字段同步（5 道）
python verify_frontend.py

# 冗余扫描

python _unused.py        # 样式类 / 常量

# 全量回归
for s in _lint verify_frontend verify_integration verify_engine verify_v26 verify_v28 \
         verify_v29 verify_v30 verify_parity verify_rrpath verify_tgam verify_collect; do
  python $s.py > /dev/null 2>&1 && echo "$s OK" || echo "$s FAIL"
done
```

# 状态判断引擎设计评估（2026-11-11）

评估对象：`state_engine.py` / `engine.js` 的判据链（门控 → 评分 → 仲裁 → 置信度 → 反馈）、
校准协议、伪迹处理、时间窗设计。

方法：读判据全表（每条常量都带依据与修订记录）+ **构造式验证**（逐状态构造"纯净触发帧"，
看是否误带其他状态）+ 真实序列复核（`output_demo --check`）。

---

## 一、总体判断

**工程实现的质量高于判据的科学强度。**

判据层的工程化程度很高：每条阈值都有文献出处或实测定标依据，每次调整都记录了"为什么改、
改前改后实测多少"（例如伪迹门限 6×→15× 附了三份 dump 的三段伪迹率对比）。这套注释密度
在国内本科项目里是罕见的，答辩时经得起追问。

但**8 个状态的证据强度差异很大**，而这一点在文档里没有被明确分层。如果笼统宣称
"8 状态判别"，会被质疑过度声称。

---

## 二、8 态判据的证据分级

| 状态 | 主判据 | 依据性质 | 等级 |
|---|---|---|---|
| **stress** | `z(RMSSD₆₀) < −1.5` | HRV 应激反应，−1.5σ 为文献值（Stephenson 2021） | **A** |
| **drowsy** | `z(TAR) > +1.5` 且 `z(δ) > +1.0` | θ/α 升高 + δ 升高是嗜睡共识；双条件合取合理 | **B+** |
| **relaxed** | `z(A_rel) > +1.5` | α 升高=放松是共识，但 A_rel 是派生量（相对基线增量），非标准指标 | **B** |
| **focus** | `z(R_tb) < −1.0` + RMSSD 不低 + 体动平静 | θ/β 与专注负相关有文献，但"排除法"三条件是工程构造 | **B** |
| **distracted** | `z(R_tb) > +1.0` + task_active | 与 focus 共用 R_tb 的两端，区分依赖单一特征 | **B−** |
| **anxiety** | `att<40 且 med<40` 或 z 双低 | 用**厂商黑盒指数**定义"焦虑"，无独立效度验证 | **C** |
| **fatigue** | `z(R_ba) < −1.0` 且 `I_f ≥ 300` | R_ba=β/(α+θ) 是工程定义；I_f 的 300s 是"人定当量"而非统计量 | **C** |
| **flow** | `att/med>60` + 稳定 5 帧 + sync 达标 + `R_tb<Z_DIST` | 5 个条件叠加，其中 sync（趋势一致性）官方无此字段 | **C** |

**建议的答辩口径**：按 A / B / C 三档说明——
「stress 有直接文献阈值；relaxed/focus/drowsy 有共识级依据 + 工程构造的门控；
anxiety/fatigue/flow 的三个特征（厂商指数、I_f 积分、sync）都是工程派生口径，
结论应表述为'与该状态一致的生理模式'，而非'诊断出该状态'。」

这个口径在文档里目前是散落在各处的（`口径与免责` 一节提到 sync 是派生口径），
**建议集中成一张表**，主动摊开比被问出来好。

## 三、构造式验证的结果

做法：以默认基线为中心，为每个状态构造"恰好触发本状态"的帧序列，观察是否**只**触发该状态。

```
构造场景                       判定         conf  同时成立的门控
基线（无偏离）                  neutral      0.60  []
stress: RMSSD z=−2             stress       0.95  [stress]              ✅ 纯净
relaxed: α 升 55%              relaxed      0.83  [relaxed]             ✅ 纯净
focus: θ/β=0.6                 focus        0.83  [focus]               ✅ 纯净
distracted: θ/β=1.5            distracted   0.95  [distracted]          ✅ 纯净
anxiety: att/med=35            anxiety      0.83  [anxiety]             ✅ 纯净
drowsy: θ/α=1.4 + δ=150        drowsy       0.81  [drowsy, distracted]  ⚠ 共现（靠优先级解决，正确）
疲劳(β=50,α=150,θ=100,I_f=350)  fatigue      0.64  [fatigue,dist,relax]  ❌ 置信度被稀释
疲劳(θ=β=60,α=240,I_f=350)      fatigue      0.61  [fatigue,relaxed]     ❌ 同上
心流(att/med 恒定 75)            neutral      0.60  []                    ❌ 判不出
心流(att/med 62→78 递增)         flow         0.95  [flow]                ✅
```

五个状态能**纯净触发**，说明判据主体是正交的。问题集中在 fatigue 和 flow。

## 四、三个结构性问题

### P1 疲劳与分心/放松在特征上必然共现，导致置信度系统性偏低

**这不是实现 bug，是判据选型的数学后果。**

`R_ba = β/(α+θ)`。要让 `R_ba` 低（疲劳门控），只能 β↓ 或 α↑：

- **β↓** → `R_tb = θ/β` 必然↑ → **distracted 门控成立**
- **α↑** → `A_rel = (α−α₀)/α₀` 必然↑ → **relaxed 门控成立**

也就是说，"疲劳"的两种生理表现，各自都会同时点亮另一个状态的门控。
置信度公式是 `conf = 0.6 + 0.35 · sep · strength`，其中
`sep = e_best / (e_best + e_second)` —— **三个状态共现时分母变大，sep 被稀释**。

实测后果：

| 场景 | conf | 是否触发提醒 |
|---|---|---|
| 我构造的强疲劳 | 0.61–0.64 | **否**（< WEAK_CONF 0.7，只记录） |
| 真实 mock 疲劳段 | 0.75 | 是（刚过阈值） |
| 其余 6 个状态 | 0.83–0.95 | 是 |

**风险**：真实受试者若"疲劳且放松"（α 高、β 低——这很常见，累到不想动），
疲劳的 conf 会跌破 0.7，系统只记录、不提醒。而疲劳正是这个项目最想干预的状态之一。

**为什么当初没暴露**：`output_demo` 的疲劳段是精心构造的"纯疲劳"（distracted/relaxed 的
evidence 都很低），所以 conf 能到 0.75。构造式验证把这个问题放大了。

**可选修法**（按侵入性从小到大）：

1. **只改置信度，不改判据**：`sep` 计算时把"与 best 结构性共现"的状态排除在分母外
   （fatigue 对 distracted/relaxed）。改动局限在 `_arbitrate`，不影响 8 段主判率。
2. **给 fatigue 加独立强度维度**：`strength` 取 `max(m_best/EVID_FULL, I_f/IF_HOLD_S)`
   —— 积分越高越确定，不依赖跨状态比较。
3. **改判据**：fatigue 门控要求 `I_f ≥ 600s` 并降低对 R_ba 的依赖。风险最高，会影响对拍
   与已验收数据。

**我倾向 1 或 2**：都不动门控，因此 `verify_parity` 的 5 道闸门与 8 段主判率全部不变，
只需重跑 conf 相关断言。

### P2 心流在"恒定高值"下判不出——与"稳定高值"的判据字面矛盾

flow 的门控包含 `sync_latched`（双指数趋势一致性，窗口 10 帧、同向占比 ≥0.6）。
同步率靠**相邻帧差分方向**计算：att/med 恒定时差分为 0，无方向、无同向帧
→ `sync_ok=False` → flow 判不出。

实测：att=med=75 **恒定** 16 帧 → `neutral`；同一数值**正弦同向波动** → `flow 0.95`。

**问题**：判据写的是"稳定于高值区间"，但实现要求"有同向变化"。一个真正进入心流、
指标又极其平稳的人，反而判不出。真实数据不会完全恒定，但这是逻辑上的自相矛盾。

**可选修法**：`sync_ok` 增加"低方差 + 双高"的旁路——当 att/med 均 > 阈值且窗口内
方差低于某门限时，视同趋势一致（"稳定"本身就是一种一致）。

### P3 neutral 占比 14–25% 是设计选择，不是缺陷

门控全部是合取（AND），条件越多越难过。真实序列里 `neutral` 占 194/765 ≈ 25%。

对"盯盘不打扰"的产品目标，这是**正确**的（不确定就不判、不干预）。
但若对外宣称"8 状态判别"，需要同时说明"约 1/4 时间判为'未确认'"。
`README` 目前只在实测表里给了分布数字，没有点明这层含义。

## 五、实现方式评估

### 做得好的四处（都有明确依据）

1. **伪迹三层设计**：中位数参照（只记有效帧）→ 单频段 15× → 逃生门（连续 60 帧重建参照）。
   三条规则各自对应一类实测失败（持续伪迹自我掩护、参照被污染、增益切换锁死），
   不是拍脑袋加的。

2. **θ_ref 取自 B 段（睁眼）而非 A 段（闭眼）**——这是整条链上最关键的一个正确决策。
   闭眼 θ 天然偏高，若用它做疲劳参照，`I_f` 永远不启动。文档里记录了这个推论过程。

3. **时间确认按"时长"而非"帧数"**：真机帧间隔 1.2–1.5s 且会掉帧，按帧数会让 0.1s 的快帧
   突发把"60% 命中"提前触发。改成按时长后确认点恒在 `DEBOUNCE_S·HIT_RATIO` 附近。

4. **置信度双维度**：`sep`（排他性）× `strength`（绝对强度）。这是对 v3.4 两次失败的正确修正
   ——先是跨量纲比分数（stress 量级 1–3 vs anxiety 量级 10–20），后是单状态时 sep 恒 1
   导致 conf 恒 0.95。

### 三处隐患

1. **肌电门默认关闭**（`ARTIFACT_EMG_GATE = False`）。
   说话/咬牙时 β、γ 同时抬升，单频段 15× 门会饱和而放过，导致朗读段的 EEG 被当有效数据。
   注释写明"等 V4 真机通过后打开"，但 V4 数据尚未采集（D3 待办）——
   这意味着**当前真机链路在"用户说话"场景下没有防护**。

2. **`DEBOUNCE_S = 5s` 对真机偏短**。真机 1.2–1.5s/帧 → 窗口内仅 3–4 帧，
   命中率按时长算的离散度很大。`_audit_engine` 与 verify 全部用 1s/帧测，
   这个参数在真机上的行为**从未被验证过**。

3. **`EVID_FULL = 0.5σ` 会让"刚过门控"直接拿满置信度**。
   注释解释为"门控阈值已在 1–1.5σ，再超 0.5σ 即明显越过"，逻辑成立；
   但结果是 conf 的取值高度集中在 0.95（8 段里 5 个是 0.95），
   **区分度主要来自 sep 而非 strength**。若将来要按 conf 分级（如 0.9 以上才强干预），
   这个标尺需要重定。

## 六、建议的处理顺序

| 优先级 | 事项 | 侵入性 | 影响面 |
|---|---|---|---|
| 1 | fatigue 置信度（P1，方案 1 或 2） | 低（只改 `_arbitrate`） | 不改门控 → 对拍与主判率不变 |
| 2 | 文档补"证据分级表"（第二节） | 零 | 只影响答辩口径 |
| 3 | 肌电门开启 | 中 | 需 V4 真机数据支撑，否则没有定标依据 |
| 4 | `DEBOUNCE_S` 真机标定 | 低 | 需一次真机采集 |
| 5 | flow 的 sync 旁路（P2） | 中 | 影响 flow 命中率 |

第 1、2 项可以立刻做；3、4 依赖真机；5 属打磨。
